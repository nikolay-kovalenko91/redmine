  C/D. Architecture options

  Option 1 — New PersonalAccessToken model + personal_access_tokens table

  Separate AR model, migration [7.2], columns: user_id, name, token_hash,
  expires_on, last_used_on, revoked_at, created_on, updated_on. Unique index on
  token_hash, index on user_id. Integration is ~6 lines inside find_current_user
  plus a prefix dispatch in the key-reading path.

  - Regression surface: lowest. Token, tokens, destroy_expired,
  delete_previous_tokens all untouched → token_test.rb and user_test.rb token
  tests cannot break.
  - Migration impact: one additive create_table. Trivially reversible. Portable
  across sqlite/pg/mysql.
  - Backward compat: total. Legacy key path is byte-for-byte unchanged.
  - Security: hash at rest (SHA-256 of a high-entropy secret — not bcrypt,
  because lookup must be by index, and the secret is already 160+ bits so a slow
  KDF buys nothing); native expiry; native revocation; per-token identity; can
  enforce must_change_password? / status uniformly.
  - Complexity: moderate — one model, one migration, one controller area, one
  view area, tests.

  Option 2 — Extend the existing Token model with a pat action

  Add name, expires_on, last_used_on columns to tokens; widen value to hold a
  hash; add_action :pat, max_instances: nil.

  - Regression surface: highest. tokens is shared by session, autologin,
  recovery, register, feeds, twofa_backup_code. Changing value's
  width/semantics, find_token's /\A[a-z0-9]+\z/i guard, delete_previous_tokens's
  max_instances logic, or destroy_expired's Arel touches all seven actions.
  token_test.rb asserts Token.destroy_expired's return count.
  - Migration impact: change_column on a hot shared table with a unique index;
  the 2013 migration already warns this "may take some time".
  - Backward compat: risk of subtle breakage in autologin/session/recovery.
  - Security: to hash PAT values you'd have to either hash everything (breaking
  autologin/recovery lookups) or make value polymorphic per action — an
  unpleasant invariant.
  - Complexity: deceptively low up front, high in verification.

  Option 3 — Mint Doorkeeper access tokens as PATs

  Reuse Doorkeeper::AccessToken with a synthetic "personal" application. Gets
  hashing (hash_token_secrets), expires_in, revoked_at, and scopes for free;
  find_current_user:134 already accepts them.

  - Regression surface: low in Redmine code, but couples PATs to Doorkeeper's
  config, which currently declares grant_flows ['authorization_code'] and
  enforce_configured_scopes.
  - Migration impact: none.
  - Backward compat: PATs would arrive as Authorization: Bearer, not via
  X-Redmine-API-Key — every existing Redmine client would need changing.
  api_key_from_request takes precedence over the Bearer branch, so a client
  sending both breaks.
  - Security: strongest primitives, but semantics are wrong: a PAT is not an
  OAuth grant, and there's no application/consent to point at. oauth_scope would
  be set, silently changing admin? and allowed_to? behaviour — a behavioural
  change the CLAUDE.md scope rules forbid without approval.
  - Complexity: low code, high conceptual and review risk.

  ---
  E. Recommendation

  Option 1, sliced as follows:

  1. PersonalAccessToken model + [7.2] migration (additive table only).
  2. Token format rmpat_<40 hex> — the prefix makes dispatch deterministic at
  the api_key_from_request seam, is greppable for secret scanning, and cannot
  collide with a legacy 40-hex key. Note Token.find_token's /\A[a-z0-9]+\z/i
  guard means a prefixed value is structurally incapable of being mistaken for a
  legacy token.
  3. Accept PATs through the existing vectors — key param, X-Redmine-API-Key
  header, HTTP Basic username — so existing clients work by swapping the string
  only.
  4. Enforce, for PATs, the invariants the legacy key misses: user active?, not
  expired, not revoked, and must_change_password? → 403 (parity with the Basic
  branch).
  5. My Account UI: list / create (with name + optional expiry) / revoke, secret
  shown exactly once, under the existing require_sudo_mode convention.
  6. Legacy API key continues to work unchanged.

  F. Explicitly deferred

  - Rate limiting (out of scope by instruction)
  - Scopes / granular endpoint control (Role#allowed_to?(action, scope) seam
  documented but unused)
  - Audit logging
  - CORS
  - Changing destroy_tokens to revoke legacy 'api' tokens on password change — a
  real hardening, but it changes existing Redmine behaviour and belongs to a
  separate decision
  - Migrating existing legacy keys to PATs
  - Admin-side PAT management for other users
  - X-Redmine-Switch-User interaction beyond inheriting current behaviour
  - Rewriting api_request? / accept_api_auth semantics

  1. Expiration semantics

  Column name: expires_on. This is not a coin-flip — the evidence is decisive. I
  mapped every datetime column in db/schema.rb to its table: every Redmine-core
  table uses _on (created_on, updated_on, last_login_on, passwd_changed_on,
  closed_on, committed_on), and every _at column belongs to a vendored or 
  generated table — oauth_access_tokens/oauth_access_grants/oauth_applications
  (doorkeeper), imports and reactions (Rails t.timestamps). tokens itself uses
  created_on/updated_on. _at would mark the table as foreign to Redmine core.

  Note _on in Redmine does not imply date-only: users.passwd_changed_on is
  t.datetime ... precision: nil (db/schema.rb:592). So t.datetime :expires_on, 
  precision: nil, null: false — precision: nil matching core convention
  (doorkeeper's tables omit it and get precision 6).

  Type: datetime, not date. A date-only expiry has an ambiguous boundary
  (midnight in whose zone?). Store the absolute instant, computed at creation as
  Time.now + n.days.

  Timezone — this is the trap. config/application.rb:37:
  config.active_record.default_timezone = :local
  and config.time_zone is left commented out (:51-53), so Time.zone is UTC while
  ActiveRecord serializes in server local time. Redmine core resolves this by
  consistently using Time.now, never Time.zone.now:

  - token.rb:70 — Time.now - validity_time
  - token.rb:123 — token.created_on > validity_days.days.ago
  - user.rb:363 — changed_on < period.days.ago (in password_expired?)

  Rule for PAT code: use Time.now, .ago, .from_now. Never Time.zone.*. Mixing
  the two produces a silent offset bug exactly equal to the server's UTC offset
  — which on a UTC server is zero, so it would pass CI and fail in production.
  This is worth a code comment.

  Boundary — exclusive at the instant of expiry:
  def expired?
    expires_on <= Time.now
  end
  Valid while Time.now < expires_on; dead at and after expires_on. precision: 
  nil means whole-second granularity, so the boundary is one second wide. The
  closest core analogue is password_expired? (user.rb:357-365), which uses the
  same plain Time comparison against a precision: nil column.

  Mandatory: null: false at the DB level, validates :expires_on, :presence => 
  true, plus a validation that it is in the future and within MAX_LIFETIME = 
  365.days. UI offers presets (30/60/90/365 days). Max lifetime is a model 
  constant, not a Setting — a Setting would drag in settings.yml, an admin view
  and an en.yml key for no required benefit. Deferred.

  2. Auth seam and dispatch — exact control flow

  The seam is find_current_user (application_controller.rb:112-173), and 
  specifically two lines: :131-133 and :152. Nothing else changes.

  api_key_from_request (:727-734) is not the right dispatch point — it returns a
  string and has no lookup responsibility. Dispatching there would also miss
  the Basic vector, which reads username directly.

  Vector 1 — ?key= query/form parameter, and Vector 2 — X-Redmine-API-Key

  Both flow through the same line, because api_key_from_request already
  collapses them (param wins over header, :729-732). Current code:

  if (key = api_key_from_request)
    user = User.find_by_api_key(key)

  Becomes:

  if (key = api_key_from_request)
    if PersonalAccessToken.pat_format?(key)
      user = PersonalAccessToken.find_active_user(key)
      if user && user.must_change_password?
        render_error :message => 'You must change your password', :status => 403
        return
      end
    else
      user = User.find_by_api_key(key)          # UNCHANGED legacy path
    end

  Vector 3 — HTTP Basic, credential as username

  Current (:142-157):
  elsif /\ABasic /i.match?(request.authorization.to_s)
    authenticate_with_http_basic do |username, password|
      user = User.try_to_login(username, password)
      if user&.twofa_active?  ... 401 ... end
      user ||= User.find_by_api_key(username)
    end
    if user && user.must_change_password?  ... 403 ... end

  Only line :152 changes:
      user ||= if PersonalAccessToken.pat_format?(username)
                 PersonalAccessToken.find_active_user(username)
               else
                 User.find_by_api_key(username)    # UNCHANGED
               end

  The must_change_password? 403 at :154-157 already sits outside the 
  authenticate_with_http_basic block and applies to whatever user resolved to — 
  so it covers PATs on this vector with zero changes. That is why the new 403
  check is needed only in the param/header branch.

  How legacy behaviour stays identical

  1. Precedence is untouched. The if/elsif/elsif chain at :131/:134/:142 is not
  reordered. A PAT in params[:key] short-circuits Doorkeeper and Basic exactly
  as a legacy key does today.
  2. User.find_by_api_key is called with byte-identical arguments on every
  legacy path. Token, tokens, find_token, delete_previous_tokens,
  destroy_expired — all untouched.
  3. The two namespaces are provably disjoint, structurally. token.rb:116:
  return nil unless action.present? && /\A[a-z0-9]+\z/i.match?(key)
  3. An rmpat_-prefixed string contains _ and therefore cannot resolve as a
  legacy token — even if pat_format? had a bug and fell through to the legacy
  branch, the result is nil, not a wrong user. Conversely a 40-hex legacy key
  can never match /\Armpat_[0-9a-f]{40}\z/. This is a safety property of the
  format choice, not merely a convention.
  4. The gate at :130 is inherited, not modified. PATs are subject to the
  identical Setting.rest_api_enabled? && accept_api_auth? condition. Atom-key
  auth (:125-127), Doorkeeper (:134-141), X-Redmine-Switch-User (:160-168),
  SysController and MailHandlerController are all untouched.

  pat_format? is a regex test with no DB hit, so the legacy path costs one extra
  regex match per request.

  3. Protecting PAT management

  Answer: a PAT cannot create or revoke a PAT, and this requires no new 
  authorization code — it falls out of the existing accept_api_auth mechanism.

  Evidence — my_controller.rb:26-29:
  accept_api_auth :account
  require_sudo_mode :account, only: :put
  require_sudo_mode :reset_atom_key, :reset_api_key, :show_api_key, :destroy

  Redmine already treats credential management as session-only: show_api_key and
  reset_api_key are absent from accept_api_auth and present in
  require_sudo_mode. I follow that exactly — new actions go in
  require_sudo_mode, and not in accept_api_auth.

  The mechanics, traced:
  1. find_current_user:130 opens the API block only if user.nil? && 
  Setting.rest_api_enabled? && accept_api_auth?.
  2. accept_api_auth? (:653-655) checks membership in the class attribute. For
  an undeclared action it is false.
  3. So the whole API block is skipped → User.current is anonymous.
  4. before_action :require_login (my_controller.rb:22) fires.
  5. require_login's format.api branch (:293-297) returns 403 Forbidden, not
  401, precisely because accept_api_auth? is false.

  This closes the escalation path where a stolen PAT mints a replacement to
  outlive its own revocation. Management therefore requires an interactive
  session.

  Honest caveat: require_sudo_mode is a no-op in a default install —
  config/configuration.yml.example:167 says "Disabled by default" and
  sudo_mode.rb:233 reads Redmine::Configuration['sudo_mode']. So the meaningful
  guard is the session requirement; sudo adds password re-confirmation only
  where an admin has enabled it. This is exactly the posture reset_api_key has
  today — we inherit it, neither improving nor weakening it. Listed as a risk
  below.

  4. Create-and-reveal flow

  The crux: the create action renders in place and never redirects. Everything
  else follows from that.

  1. Generation is in-memory. The model exposes attr_reader :plain_token backed
  by an ivar. There is no plain_token column in the migration, so ActiveRecord
  physically cannot persist it — the guarantee is structural, not a discipline.
  def generate_token!
    @plain_token = "#{PREFIX}#{Redmine::Utils.random_hex(20)}"
    self.token_hash = self.class.hash_token(@plain_token)
  end
  1. Reuses Redmine::Utils.random_hex, the same generator as token.rb:129.
  2. Not in the URL, not in flash. On success the controller assigns and renders
  the list template with a reveal panel:
  if @pat.save
    @created_token_value = @pat.plain_token
    render :action => 'personal_access_tokens'
  end
  2. A redirect_to would force the value into flash or a query string. This is a
  deliberate divergence from reset_api_key (my_controller.rb:139-150), which
  can redirect because the sidebar re-reads plaintext from the DB — an option we
  gave up by hashing.
  3. Not in the session. Nothing is written to session. Refreshing the page
  renders the list without the secret; there is no second chance by design.
  4. Not in logs. config/application.rb:68 is config.filter_parameters += 
  [:password]. At creation the token is generated server-side and is never an
  inbound parameter, so it never reaches a params log line. Rails does not log
  response bodies. No filter_parameters change is needed for the create flow.

  4. But I found a real adjacent issue you should decide on: at authentication
  time, ?key=<credential> is an inbound parameter, and :key is not filtered — so
  Redmine logs API credentials in plaintext today, for legacy keys and (unless
  changed) for PATs. Adding :key to filter_parameters is a one-line, low-risk
  hardening, but it alters existing logging behaviour, so per your CLAUDE.md
  rules I am not doing it silently. It sits in the deferred list as a flagged
  sub-decision. Say the word and it moves into scope.
  5. Not recoverable. Only the SHA-256 hex is stored. Losing the value means
  creating a new PAT.

  Display reuses the existing Stimulus copy controller at
  app/javascript/controllers/api_key_copy_controller.js.

  updated_on — omitted. Nothing mutates a PAT after creation: no rename, no
  last_used_on, revocation is a DELETE. tokens carries it only because
  delete_previous_tokens orders by it (token.rb:139). An always-null column
  earns nothing; add_column later is trivial.

  last_used_on — omitted, and I agree with the instinct behind your question. If
  tracking is deferred, the column is a false affordance in both the schema and
  the UI — "Last used: never" would read as a fact when it is an artifact. It
  is a purely additive add_column whenever you want it, no cheaper now than
  later.

  Revocation: physical DELETE, not revoked_at. Three reasons:

  1. Redmine precedent is unanimous. Every credential revocation in core is
  physical: token.rb:144 scope.delete_all, user.rb:966
  Token.where(...).delete_all, user.rb:993 Token.where('user_id = ?', 
  id).delete_all, my_controller.rb:145 User.current.api_token.destroy. There is
  no soft-delete or tombstone pattern for credentials anywhere in Redmine.
  Doorkeeper uses revoked_at, but it is a vendored gem needing it for
  refresh-token rotation, which we do not have.
  2. Fail-safe defaults. revoked_at means every lookup must carry revoked_at IS 
  NULL. A forgotten condition is an authentication bypass. With deletion, a
  missing condition cannot exist — the row is gone and the lookup finds nothing.
  3. revoked_at earns its keep only as an audit trail, and audit logging is
  explicitly deferred.

  Accepted trade-off: no record that a token existed and was revoked.

  Index portability, per your instruction: both are plain single-column B-trees
  — a unique index on a string(64) and a plain index on an integer. No partial,
  functional, or expression indexes. Safe on sqlite3, postgresql and mysql2 (the
  .github/workflows/tests.yml:11-15 matrix); a varchar(64) is far under MySQL's
  index-prefix limits.

  ────────────────────────────────────────

  Behaviour: PATs deleted
  Basis: has_many :personal_access_tokens, :dependent => :delete_all. Required

  ────────────────────────────────────────
  Rule: 2FA: no effect on PATs
  Behaviour: PATs work regardless of 2FA state
  Basis: This is intended design, not a gap. application_controller.rb:146-150
  blocks Basic username/password when twofa_active? with the message "HTTP  
  Basic authentication is not allowed. Use API key instead" — Redmine's
  explicit position is that token credentials are the 2FA-compatible path.
  Blocking PATs would contradict the product's own instruction.
  must_activate_twofa? is session-flag-driven (:94-98) and inert for tokens.
  ────────────────────────────────────────
  Rule: Password change revokes PATs
  Behaviour: after_save on saved_change_to_hashed_password? deletes the user's

  Basis: See below.

  On the password-change rule: user.rb:958-967 destroy_tokens deletes
  ['recovery','autologin','session'] and deliberately excludes 'api' — legacy
  keys survive password changes. I recommend PATs do not, because a password
  change is the canonical "I may be compromised" action and a surviving
  credential defeats the feature's purpose. Crucially this is new behaviour for 
  a new mechanism, implemented as a separate callback — it does not touch
  destroy_tokens and does not change legacy behaviour, so it stays inside your
  "preserve existing Redmine behaviour" constraint.

  Counter-argument, so you can overrule with full information: GitHub does not 
  revoke PATs on password change, and this makes PATs less drop-in than the
  legacy key (rotate your password, every integration breaks). If you prefer
  PATs to match legacy survival semantics, say so and I will drop this callback
  — it is one isolated method.

  Unrelated legacy hardening — deferred, not done

  - Adding 'api' to user.rb:962 destroy_tokens (would revoke legacy keys on
  password change) — changes existing behaviour.
  - Adding :key to config.filter_parameters (application.rb:68) — changes
  existing logging.
  - Eagerly deleting PAT rows when an account is locked — unnecessary; the
  lookup-time active? check is already equivalent and simpler.
  - Enforcing must_change_password? on the legacy param/header vector.

  7. Committed lifecycle vs deferred

  Committed — self-service, My Account, session-only:

  1. List — name, created, expires, expired badge (GET 
  /my/personal_access_tokens)
  2. Create — name + expiry preset, plaintext revealed exactly once (POST)
  3. Revoke — physical delete, effective immediately (DELETE .../:id)
  4. Authenticate — all three existing vectors
  5. Reject — unknown / expired / revoked / inactive / must-change-password
  6. Legacy API key unchanged, proven by the existing authentication_test.rb
  staying green plus explicit regression tests

  Routes follow the hand-written style of the neighbouring my/ block
  (config/routes.rb:92-103), not resources. I chose the verbose
  my/personal_access_tokens over a short my/pats so it cannot be confused with
  the legacy "API key" in URLs, logs, or the UI — Redmine already writes long
  paths (users/:user_id/twofa/deactivate, :116).

  Deferred, explicitly: rate limiting (instructed) · scopes / granular endpoint
  control · audit logging · CORS · last_used_on · admin management of other
  users' PATs · legacy→PAT migration · a Setting to disable legacy keys · the
  two legacy-hardening items above · bulk cleanup of expired rows (cf.
  Token.destroy_expired, called only from lib/tasks/redmine.rake:39, i.e. never
  automatically) · REST endpoints for PAT management (deliberately excluded per
  Q3) · configurable max lifetime · any change to X-Redmine-Switch-User.

  On scopes specifically — the seam already exists and I am documenting it
  without using it: Role#allowed_to?(action, scope) (role.rb:204-210, :304-311),
  User#allowed_to? threading @oauth_scope (user.rb:770, :789), and User#admin?
  (user.rb:736-744). A future PAT scope would set the same ivar. No code now.

  The three most important trade-offs / risks

  1. Prefix-based dispatch is the security-critical hinge. The entire "legacy is
  untouched" claim rests on pat_format? partitioning the credential space
  correctly. The mitigation is strong — token.rb:116's /\A[a-z0-9]+\z/i guard
  makes a rmpat_-prefixed string structurally unresolvable as a legacy token, so
  even a dispatch bug fails closed rather than authenticating the wrong user.
  But the converse is untested by construction: if a future change relaxed that
  guard, or if pat_format? were loosened, the partition would silently weaken.
  Mitigation: a strict anchored regex (/\Armpat_[0-9a-f]{40}\z/, not 
  start_with?), plus an explicit test asserting that a PAT value passed to 
  User.find_by_api_key returns nil.

  2. Hashing forecloses recovery, and the reveal flow is the only chance. Unlike
  reset_api_key, which re-reads plaintext from the DB forever, a lost PAT is
  gone. This is the correct security property but it is a genuine UX regression
  relative to the legacy key, and it makes the create action's
  render-don't-redirect requirement load-bearing: a future refactor that
  "tidies" it into a redirect would either break the feature or push the secret
  into flash. Mitigation: a comment at the call site, and a test asserting the 
  plaintext is absent from a follow-up GET.

  3. Management protection depends on an absence, and sudo mode is off by 
  default. "A PAT cannot mint a PAT" is enforced by not listing the actions in
  accept_api_auth — a negative invariant, invisible at the point it protects,
  and silently destroyed by anyone who later adds accept_api_auth 
  :personal_access_tokens for convenience. Compounding it, require_sudo_mode is
  a no-op in a default install (configuration.yml.example:167), so the real
  guard is the session requirement alone. This is no weaker than reset_api_key
  today, but it is weaker than it looks on paper. Mitigation: test case 10 (POST
  /my/personal_access_tokens.json with a PAT → 403) exists specifically to fail
  loudly if the absence is ever filled in.

  actionpack/lib/action_dispatch/http/filter_parameters.rb:45-46 builds it from

  Are they alternatives?

  Not really — they cover different halves, which is the main point:

  - filter_parameters is the only option that helps legacy keys, since backward
  compatibility forbids removing ?key= for them.
  - Forbidding query-param auth for PATs is the only option that removes
  exposure outside Rails logs, and it's nearly free because there are no
  existing PAT clients to break.

  Note on the one-liner: ActiveSupport::ParameterFilter treats a Symbol as a
  substring match, so :key also redacts api_key, atom_key, keywords, etc. Use
  /\Akey\z/ if you want exact-match only.

  Exposure remaining if you only add :key

  Rails logs get clean; the credential is still in the URL, so it survives in:

  1. Reverse-proxy / web-server access logs — nginx $request, Apache %r, HAProxy
  log the raw request line. filter_parameters has zero reach here. Biggest one
  in practice.
  2. Referer leakage to third parties — and this is sharper in Redmine than
  usual: application_controller.rb:130 is not gated on api_request?, so an API
  key authenticates HTML responses on accept_api_auth actions. An HTML page
  fetched with ?key= will leak the full URL in Referer on any outbound link.
  3. Browser history, bookmarks, address bar — API/feed URLs get pasted into
  browsers routinely.
  4. Copy-paste propagation — the URL carries the credential into tickets, chat,
  docs, screenshots.
  5. Intermediaries — CDN/WAF/corporate TLS-terminating proxy logs.
  6. Rails error pages / exception reporters — request.url and original_url in a
  backtrace are not filtered by filter_parameters.

  Headers and Basic auth avoid all six, since neither nginx nor Rails logs them
  by default.

  Recommendation

  Do both, as separate decisions:

  - :key filter — take it. Smallest possible change, helps legacy keys (which
  nothing else can), no compat risk. Still needs your sign-off since it alters
  existing logging.
  - PATs header/Basic only — I'd now lean toward taking this too, and would
  revise my earlier plan accordingly. It's the only thing that addresses items
  1–6, and the compat argument against it is weak precisely because PATs are
  new. The cost is that PATs stop being a pure drop-in string swap for ?key=
  users, which is a real but acceptable UX regression for a credential we're
  already making non-recoverable.

  If you want the middle path: accept ?key= for PATs but log a deprecation
  warning — though that adds a code path to test for little gain.

     │ Design                                                                  │
     │                                                                         │
     │ Token format                                                            │
     │                                                                         │
     │ pat_ + 40 lowercase hex (Redmine::Utils.random_hex(20), 160 bits) = 44  │
     │ chars.                                                                  │
     │ Namespaces are provably disjoint: token.rb:116's /\A[a-z0-9]+\z/i guard │
     │ means a                                                                 │
     │ pat_-prefixed string can never resolve as a legacy token even if        │
     │ dispatch were buggy.                                                    │
     │                                                                         │
     │ Transport — header and HTTP Basic only, never a query parameter         │
     │                                                                         │
     │ PATs are accepted in X-Redmine-API-Key and as the HTTP Basic username.  │
     │ They are                                                                │
     │ not accepted in ?key=, because a URL-borne credential survives in       │
     │ reverse-proxy                                                           │
     │ access logs, Referer headers, browser history and pasted links — none   │
     │ of which                                                                │
     │ config.filter_parameters can reach. Legacy keys keep ?key= unchanged.   │
     │                                                                         │
     │ This needs no rejection code: a PAT sent as ?key= falls to              │
     │ User.find_by_api_key,                                                   │
     │ which returns nil via the token.rb:116 guard. The dispatch simply does  │
     │ not attempt a                                                           │
     │ PAT lookup when the value came from the parameter.                      │
     │                                                                         │
     │ Storage                                                                 │
     │                                                                         │
     │ SHA-256 hex (64 chars) in token_hash, unique-indexed. Plaintext exists  │
     │ only in memory                                                          │
     │ and is returned once by the create action. Not bcrypt: the secret is    │
     │ already 160 random                                                      │
     │ bits, so a slow KDF buys nothing and would forbid an indexed lookup.    │
     │                                                                         │
     │ Schema — db/migrate/<ts>_create_personal_access_tokens.rb ([7.2])       │
     │                                                                         │
     │ create_table :personal_access_tokens do |t|                             │
     │   t.integer  :user_id,    null: false                                   │
     │   t.string   :name,       limit: 60, null: false                        │
     │   t.string   :token_hash, limit: 64, null: false                        │
     │   t.date     :expires_on, null: false                                   │
     │   t.datetime :created_on, precision: nil, null: false                   │
     │ end                                                                     │
     │ add_index :personal_access_tokens, :token_hash, unique: true            │
     │ add_index :personal_access_tokens, :user_id                             │
     │                                                                         │
     │ expires_on is a date, matching the "midnight at the start of the next   │
     │ day"                                                                    │
     │ boundary and Redmine's own t.date columns (due_date, effective_date,    │
     │ spent_on).                                                              │

     │ comparison.                                                             │

     Personal Access Tokens for the Redmine REST API (#43881)

     Context

     Redmine 6.1.2's REST API credential is a single, per-user, plaintext,
     never-expiring
     string in tokens.value (db/schema.rb:549-557, token.rb:39). It cannot be
     named,
     cannot expire, and cannot be individually revoked.

     This plan adds Personal Access Tokens as a parallel, additive mechanism:
     multiple
     named tokens per user, hashed at rest, mandatory expiry, individually
     revocable,
     self-service in My Account. The legacy API key path is left byte-for-byte
     unchanged.

     Rate limiting, scopes, audit logging and CORS are out of scope.

     Design

     Token format

     pat_ + 40 lowercase hex (Redmine::Utils.random_hex(20), 160 bits) = 44
     chars.
     Namespaces are provably disjoint: token.rb:116's /\A[a-z0-9]+\z/i guard
     means a
     pat_-prefixed string can never resolve as a legacy token even if dispatch
     were buggy.

     Transport — header and HTTP Basic only, never a query parameter

     PATs are accepted in X-Redmine-API-Key and as the HTTP Basic username. They
     are
     not accepted in ?key=, because a URL-borne credential survives in
     reverse-proxy
     access logs, Referer headers, browser history and pasted links — none of
     which
     config.filter_parameters can reach. Legacy keys keep ?key= unchanged.

     This needs no rejection code: a PAT sent as ?key= falls to
     User.find_by_api_key,
     which returns nil via the token.rb:116 guard. The dispatch simply does not
     attempt a
     PAT lookup when the value came from the parameter.

     Storage

     SHA-256 hex (64 chars) in token_hash, unique-indexed. Plaintext exists only
     in memory
     and is returned once by the create action. Not bcrypt: the secret is
     already 160 random
     bits, so a slow KDF buys nothing and would forbid an indexed lookup.

     Schema — db/migrate/<ts>_create_personal_access_tokens.rb ([7.2])

     create_table :personal_access_tokens do |t|
       t.integer  :user_id,    null: false
       t.string   :name,       limit: 60, null: false
       t.string   :token_hash, limit: 64, null: false
       t.date     :expires_on, null: false
       t.datetime :created_on, precision: nil, null: false
     end
     add_index :personal_access_tokens, :token_hash, unique: true
     add_index :personal_access_tokens, :user_id

     expires_on is a date, matching the "midnight at the start of the next day"
     boundary and Redmine's own t.date columns (due_date, effective_date,
     spent_on).
     A date column removes all timezone-serialization subtlety from the
     comparison.

     Both indexes are plain single-column B-trees — portable across the CI
     matrix.
     No updated_on (nothing mutates a PAT), no last_used_on (deferred), no
     revoked_at
     (revocation is physical DELETE, matching token.rb:144, user.rb:966,
     user.rb:993,
     my_controller.rb:145 — Redmine has no soft-delete pattern for credentials).

     Model — app/models/personal_access_token.rb

     Mirrors Token's find_token / find_user / find_active_user trio
     (token.rb:96-126):

     PREFIX        = 'pat_'
     TOKEN_PATTERN = /\Apat_[0-9a-f]{40}\z/

     belongs_to :user, :optional => false
     validates :name,       :presence => true, :length => {:maximum => 60}
     validates :expires_on, :presence => true          # -> "Expiration date is 
     required"
     validate  :expires_on_cannot_be_in_the_past

     def self.pat_format?(key)      # cheap gate, no DB hit
     def self.hash_token(plain)     # Digest::SHA256.hexdigest
     def self.find_token(plain)     # format -> hash lookup -> secure_compare ->
     expired?
     def self.find_user(plain)
     def self.find_active_user(plain)   # + user.active?
     def expired?                   # expires_on < Date.today
     def generate_token!            # sets @plain_token + token_hash
     attr_reader :plain_token       # ivar only — no column, cannot be persisted

     Expiry boundary. The token is valid through the whole of expires_on and
     dies at
     midnight starting the next day, i.e. expired? is expires_on < Date.today.
     Date.today
     (system-local) is used rather than User.current.today because User.current
     is not yet
     resolved during authentication; it is exactly the fallback branch of
     User#today
     (user.rb:584-588) and keeps the decision independent of any display
     preference.

     No default expiry and no maximum lifetime. The user must supply a date; a
     blank field
     fails validation with "Expiration date is required". A past date is
     rejected; today is
     accepted (a one-day token).

     :optional => false is explicit and load-bearing, not decorative: Redmine
     sets no
     config.load_defaults, so belongs_to_required_by_default is falsy (see
     Verified facts)
     and a bare belongs_to would accept an ownerless token. Token relies on that
     laxity
     deliberately (token.rb:21, test/unit/token_test.rb:27-32 saves a userless
     token); a
     PAT must not. It also validates that the association resolves, so a
     dangling
     user_id pointing at no row is rejected, not merely a nil one.

     User: has_many :personal_access_tokens, :dependent => :delete_all. That is
     the only
     change to User — no revocation-on-password-change callback.

     No must_change_password? check is added. PATs authenticated via HTTP Basic
     are covered
     by the pre-existing check at :154-157 (which sits outside the
     authenticate_with_http_basic block and applies to whatever user resolved
     to); PATs
     via the header are not. This asymmetry is inherited from Redmine 6.1.2, not
     introduced
     here — legacy keys behave identically today. No new authentication policy
     is added.

     Precedence, the rest_api_enabled? / accept_api_auth? gate, Doorkeeper,
     atom-key auth
     and X-Redmine-Switch-User are all untouched.

     Management — MyController, session + sudo only

     Add the three actions to require_sudo_mode (my_controller.rb:29). Do not
     add them
     to accept_api_auth (:26). Consequence, with no extra code:
     find_current_user:130
     requires accept_api_auth?, so a PAT-authenticated request never
     authenticates against
     these actions → before_action :require_login (my_controller.rb:22) → 403
     via
     application_controller.rb:293-297. A PAT cannot mint or revoke a PAT.

     Revocation scopes the lookup to the owner:
     @pat = User.current.personal_access_tokens.find(params[:id])   # 404 for 
     other users

     Create renders in place, never redirects, so the plaintext reaches the
     response body
     without touching flash, session or a URL. This diverges deliberately from
     reset_api_key
     (my_controller.rb:139-150), which can redirect only because it re-reads
     plaintext from
     the DB — an option hashing removes.

     Focused, during implementation:
     - bin/rails test test/unit/personal_access_token_test.rb
     - bin/rails test test/integration/api_test/authentication_test.rb (must
     stay green — proves legacy untouched)
     - bin/rails test test/unit/token_test.rb test/unit/user_test.rb
     - bin/rails test test/functional/my_controller_test.rb
     - bin/rails test test/integration/api_test/disabled_rest_api_test.rb

     Required test cases:
     1. Happy path — X-Redmine-API-Key header → 200; HTTP Basic username → 200
     2. PAT via ?key= → 401 (query-parameter auth forbidden)
     3. Unknown token → 401
     4. Expiry boundary: expires_on = Date.today → valid; expires_on = 
     Date.today - 1 → 401
     5. Revoked (row deleted) → 401
     6. Locked user (STATUS_LOCKED) → 401; registered user → 401
     7. PAT rejected when Setting.rest_api_enabled = '0'
     8. PAT rejected on an action without accept_api_auth
     9. Legacy 40-hex key still works via ?key=, header and Basic (regression)
     10. POST /my/personal_access_tokens.json with a PAT → 403 (no privilege
     escalation)
     11. User A cannot revoke User B's PAT → 404, and B's token still
     authenticates
     12. Plaintext appears in the create response exactly once; a follow-up GET
     does not contain it
     13. token_hash in DB ≠ plaintext; no column holds plaintext
     14. Blank expiry → validation error "Expiration date is required"; past
     date rejected
     15. user.destroy destroys the user's PATs
     16. A PAT value passed to User.find_by_api_key returns nil (namespace
     disjointness)
     17. A PAT without a valid user cannot be created — user nil → invalid, and
     user_id pointing at a nonexistent row → invalid (proves :optional => false
     validates association resolution, not just presence of the id)

     Mandatory gates before completion:
     1. bundle exec rubocop
     2. bundle exec rake test
     3. bundle exec rails db:migrate from the stock 6.1.2 schema, then
     db:rollback
     4. App boots after migration
     5. Manual curl happy path via header and Basic; manual check that
     ?key=<pat> is rejected
